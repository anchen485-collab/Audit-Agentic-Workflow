# 企业录入审批 Agent 业务说明

## 1. 项目目标

本项目要实现一个企业录入审批 Agent，用来审核员工在 Excel 中录入的企业分类是否合理。

系统不是简单检查 Excel 字段，而是把员工录入、外部企业证据、内部分类规则、LLM 语义判断、风险分层和人工复核串成一个可追踪的审批流程。

首版目标：

- 支持批量 Excel 上传和解析。
- 支持企业外部证据采集，首版使用 mock，后续参考旧项目接入官网爬虫。
- 支持内部分类规则召回。
- 支持 LLM 语义分类判断，但不让 LLM 直接决定审批动作。
- 支持自动通过、自动驳回、证据不足、人工复核四类分流。
- 支持结果 Excel 导出、Agent trace 和评测指标。

## 2. 业务痛点

企业内部的分类录入通常依赖人工审核，主要问题有：

- 人工审核成本高，批量 Excel 记录越多，审核耗时越长。
- 审核标准容易不一致，不同审核员对同一企业可能给出不同判断。
- 审核过程不可追踪，事后很难解释某条记录为什么通过或驳回。
- 低风险记录占用人工时间，高风险记录反而不一定被优先关注。
- 如果只靠固定规则，遇到企业业务描述和分类语义匹配的问题时容易误判。

本项目的价值是：用 Agent 工作流把审批过程拆成多个可测试、可观测、可兜底的判断节点，让低风险记录自动处理，让不确定记录进入人工复核。

## 3. 业务角色

### 3.1 录入员工

录入员工负责在 Excel 中填写企业信息和分类信息。

首版输入字段包括：

- 日期
- 姓名
- 一级分类
- 细分
- 企业名称&官网

### 3.2 审批 Agent

审批 Agent 负责自动读取 Excel，采集证据，召回规则，判断录入是否合理，并输出审批结论。

它包含多个职责节点：

- Intake Agent：把 Excel 原始行转成标准审批单。
- Evidence Agent：采集或模拟企业外部证据。
- Rule Agent：召回内部分类候选规则。
- Classification Agent：判断外部证据是否支持候选分类。
- Risk Agent：根据证据质量、规则命中和 LLM 结果评估风险。
- Decision Agent：根据确定性规则给出最终审批动作。
- Explanation Agent：生成审核员和录入员工可读的解释。

### 3.3 人工审核员

人工审核员不处理所有记录，只处理系统主动分流出来的不确定或高风险记录。

典型场景：

- 证据不足。
- 分类不存在。
- LLM 输出异常。
- LLM 置信度低。
- 外部证据和内部规则冲突。
- 系统判断为高风险。

## 4. 审批对象

系统审核的是一条员工录入记录是否合理。

一条记录会被标准化为审批单，核心字段包括：

- case_id：审批单 ID。
- batch_id：批次 ID。
- row_number：Excel 行号。
- employee_name：录入员工。
- company_raw：原始企业字段。
- company_name：清洗后的企业名称。
- website_url：官网 URL。
- entered_level1：员工录入一级分类。
- entered_subcategory：员工录入细分。
- entered_stage：员工录入环节。
- status：处理状态。

## 5. 审批流程

```text
员工上传 Excel
  -> 读取 Excel
  -> 创建审批单
  -> 采集企业外部证据
  -> 召回内部分类规则
  -> LLM 判断证据是否支持分类
  -> 风险评估
  -> 审批分流
       -> 自动通过
       -> 自动驳回
       -> 证据不足
       -> 人工复核
  -> 导出结果 Excel
  -> 输出质量指标和 Agent trace
```

## 6. 四类审批结果

### 6.1 自动通过

适用条件：

- 必填字段完整。
- 企业证据质量较高。
- 员工录入分类存在于内部规则表。
- LLM 判断外部证据支持该分类。
- 风险等级低。

业务含义：

这类记录置信度高，可以减少人工审核工作量。

### 6.2 自动驳回

适用条件：

- 企业证据质量足够。
- 员工录入分类与外部证据明显不匹配。
- 系统能给出有效建议分类。
- 风险规则允许自动驳回。

业务含义：

这类记录错误较明显，可以自动驳回并给录入员工修改建议。

### 6.3 证据不足

适用条件：

- 企业官网缺失。
- 官网无法访问。
- 外部证据文本为空或质量太低。
- mock provider 或真实 provider 返回失败。

业务含义：

系统不会在证据不足时强行判断，避免乱批或乱驳回。

### 6.4 人工复核

适用条件：

- 分类不存在。
- LLM 输出不是合法 JSON。
- LLM 编造候选规则之外的分类。
- 置信度低。
- 规则和 LLM 结果冲突。
- 风险等级中高。

业务含义：

人工复核是审批系统的安全阀，不是失败补丁。它保证系统只自动处理低风险记录，把复杂情况交给人。

## 7. 为什么不是普通 Excel 脚本

普通 Excel 脚本通常是线性流程：

```text
读取 Excel
  -> 检查字段
  -> if/else 规则判断
  -> 写回结果
```

这个项目不同，它处理的是不确定审批问题：

- 数据来源不只 Excel，还包括外部企业证据和内部分类规则。
- 判断方式不只是 if/else，还包括规则召回、语义判断和风险分层。
- LLM 不直接决定审批动作，而是只做语义判断。
- 每个 Agent 节点都有明确输入、输出、trace 和失败兜底。
- 高风险记录会进入人工复核。
- 最终用 golden cases、准确率、自动通过率、人工复核率等指标证明有效。

一句话总结：

> 脚本是在处理表格，审批 Agent 是在模拟一个可追踪、可兜底、可评测的人机协同审批流程。

## 8. 确定性代码和 LLM 的边界

### 8.1 交给确定性代码

- Excel 解析。
- 字段清洗。
- 必填校验。
- 官网爬虫或 mock provider 调用。
- 内部规则加载。
- 候选规则召回。
- LLM 输出 JSON schema 校验。
- 候选分类合法性校验。
- 风险阈值计算。
- 最终审批路由。
- 人工复核任务生成。
- 结果导出。

这些能力必须可测试、可复现、可解释。

### 8.2 交给 LLM

- 判断外部证据是否支持候选分类。
- 总结证据和分类之间的语义关系。
- 生成业务可读解释。

LLM 不拥有最终审批权。

核心原则：

> 代码管流程和边界，LLM 管语义理解。

## 9. LLM 失败兜底

系统不假设 LLM 永远正确。常见异常包括：

- LLM 输出不是 JSON。
- LLM 少字段或字段类型错误。
- LLM 编造候选规则之外的分类。
- LLM 置信度虚高。
- LLM 调用超时或失败。

兜底策略：

- 使用 JSON schema 校验输出。
- 只允许 LLM 从候选规则中选择分类。
- 使用证据质量分、置信度阈值和风险规则二次校验。
- 异常记录进入人工复核或证据不足。
- 用 golden cases 做回归评测。

## 10. 可量化成果指标

本项目最终要能用数字体现价值。首版要持续记录：

| 指标 | 含义 | 首版目标 |
|---|---|---|
| golden_case_count | 人工标注评测样例数 | >= 30 |
| accuracy | 审批动作准确率 | >= 80% |
| auto_approval_rate | 自动通过率 | 有明确统计 |
| auto_rejection_rate | 自动驳回率 | 有明确统计 |
| human_review_rate | 人工复核率 | 有明确统计 |
| insufficient_evidence_rate | 证据不足率 | 有明确统计 |
| llm_failure_rate | LLM 失败率 | 有明确统计 |
| average_latency_ms | 平均单条审批耗时 | 有明确统计 |
| test_count | 测试用例数量 | 持续增长 |
| e2e_pass_rate | 端到端测试通过率 | 100% |

## 11. Day 1 面试口径

如果面试官问“你这个项目解决什么问题”，可以这样回答：

> 公司内部企业分类录入需要人工审核，人工成本高，而且标准不一致、过程不可追踪。我的项目把这个流程做成审批 Agent，通过 Excel 解析、企业证据采集、内部规则召回、LLM 语义判断、风险分层和人工复核，把低风险记录自动通过或驳回，把不确定记录交给人工。最终用 trace 和 golden cases 指标证明系统可解释、可评测、可部署。

如果面试官问“为什么不是 Excel 脚本”，可以这样回答：

> 如果只是检查字段和关键词匹配，那确实是脚本。但这个系统会结合外部企业证据和内部分类规则，把审批拆成 Evidence、Rule、Classification、Risk、Decision 等节点。每个节点都有结构化输出、测试、trace 和失败兜底，LLM 只负责语义判断，最终审批动作由确定性规则控制，所以它是一个人机协同的审批 Agent 系统。
